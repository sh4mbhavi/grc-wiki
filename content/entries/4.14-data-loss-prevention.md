:::lede
Data loss prevention is the set of controls that **detects, and where configured
blocks, sensitive data moving out of approved channels** — a customer list
attached to a personal webmail, source code pushed to a public repository, a
card number pasted into a chat tool.
:::

DLP only works on data it can recognise, which is why it is downstream of
classification. A tool told to watch for "confidential" material has to be given
a definition it can match — a regex for account numbers, a fingerprint of a
document set, an exact-match list of customer records. The quality of that
definition, not the product, decides whether the control catches real leaks or
drowns the team in noise.

It also cannot tell intent from accident. The same alert fires whether an
employee is stealing a database on their last day or a salesperson is emailing a
contract to the client who asked for it. Every DLP programme is therefore a
tuning programme: the initial deployment is the easy 20%, and classifying data
and cutting false positives is the rest.

## The three states, and where controls sit

:::terms
Data in use :: On the endpoint — copy to USB, print, screen capture, paste into an unmanaged application. Endpoint DLP agents enforce here and are the only place some channels can be seen at all.
Data in motion :: Leaving the network — email, web upload, API. Network and email DLP inspect this traffic; encryption to destinations the inspection point cannot see is the standing blind spot.
Data at rest :: Sitting in a store — a shared drive, a SaaS tenancy, an object bucket. Discovery scans find sensitive data in the wrong place so it can be moved or removed before it leaks.
:::

:::def term="Data classification" ref="4.11"
The scheme that labels data by sensitivity — public, internal, confidential,
restricted — and the rules attached to each label. DLP enforces those rules;
without the scheme it has nothing to enforce and defaults to blunt pattern
matching.
:::

## Monitor before you block

Almost every failed rollout is one that switched to blocking on day one.
Legitimate business workflows move sensitive data constantly, and a blocking
rule tuned on assumptions rather than observed traffic stops deals, invoices and
support cases within hours. The programme is then switched off under pressure
and the control is lost entirely.

The workable sequence is: deploy in monitor-only mode, watch real traffic for
weeks, build an allowlist of the legitimate flows the alerts reveal, and only
then enable blocking on the narrow set of cases that are unambiguous —
restricted data to personal webmail, card data to file-sharing sites. Widen from
there as confidence grows.

## Where DLP fails

**Blocking from the start.** Rules go live in enforcement mode, break routine
work, and the business demands the tool be disabled.

**No classification behind it.** The tool matches generic patterns only, so it
misses the sensitive document that contains no account numbers and flags every
email that mentions a price.

**Alerts with no triage owner.** Thousands of low-quality alerts, nobody
assigned to work them, and the real exfiltration is somewhere in the queue that
nobody reads.

**Unmanaged channels.** Endpoint agents on laptops only, so data walks out
through a personal phone, a screenshot or a channel the inspection point cannot
decrypt.

## Common questions

:::faq
### What is data loss prevention?

A category of security control that identifies sensitive data and monitors or
prevents it leaving authorised locations and channels. DLP operates on data in
use (endpoints), in motion (network and email) and at rest (stored
repositories), and depends on a data classification scheme to know what to
protect.

### What is the difference between endpoint DLP and network DLP?

Endpoint DLP runs as an agent on user devices and can see local actions —
copying to USB, printing, pasting into applications — that never touch the
network. Network DLP inspects traffic leaving the organisation, mainly email and
web uploads. Comprehensive programmes use both, because each covers channels the
other cannot.

### Why does DLP generate so many false positives?

Because it matches patterns and cannot judge intent or context. A rule that
catches account numbers also catches every legitimate email that contains one.
Reducing false positives requires accurate data classification and weeks of
tuning against real traffic, which is the bulk of the effort in any DLP
programme.

### Should DLP be set to block or just alert?

Start in alert-only mode to learn the legitimate data flows, then enable
blocking narrowly for the cases that are never acceptable, such as restricted
data sent to personal email. Switching straight to blocking usually breaks
business processes and gets the tool disabled.
:::
