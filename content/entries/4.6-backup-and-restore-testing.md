:::lede
The control is the **restore test, not the existence of a backup** — an untested
backup is an assumption, and the only proof a backup works is a restore that
produced usable data inside the required time.
:::

A backup that has never been restored is a cost with an unproven benefit. It
occupies storage, sits on the control list and reassures nobody who has actually
needed one, because the ways a backup fails live almost entirely on the restore
side — media that cannot be read, a key nobody kept, a set that was always
missing a table. None of those show up while the backup job is the only thing
anyone watches.

This is why an auditor testing information backup under ISO/IEC 27001 Annex A
control 8.13 — which requires backup copies to be maintained and regularly tested —
or recovery under Trust Services criterion A1.3, asks to see a restore that
happened rather than a backup schedule that runs. The schedule is the assumption;
the restore is the evidence.

## What the restore has to prove

A restore test is where the recovery point objective and recovery time objective
stop being aspirations. The [business impact analysis](/risk/business-impact-analysis/)
sets both — how much data the organisation can afford to lose (the RPO) and how
long it can afford to be without the activity (the RTO) — and those numbers are
derived from the impact of the outage, not picked by whoever runs the backup
tool. A restore either returns data recent enough to meet the RPO, within the
restore-time budget the RTO allows, or it does not. The full activity recovery
time is proven by an end-to-end recovery exercise — of which the data restore is
one part; see [business continuity](/risk/business-continuity/) at 3.6. Nothing
short of an actual restore tells you whether the data half will hold.

:::def term="Recovery point objective" ref="3.7"
The maximum tolerable data loss, expressed as a length of time rather than a
volume — the point in the past back to which data must be recoverable. A restore
that returns data older than the RPO has failed even if every file it produces
opens cleanly.
:::

## What a real restore test involves

A real restore test recovers the data into a clean, separate environment — never
over the top of live production and never back into the system that just failed —
and then someone confirms the recovered data is complete and usable. Usable means
opened, queried and reconciled against a known record; a job that reports success
has told you it finished writing, not that what it wrote can be read back. The
restore is timed, from start to usable, and that figure is measured against the
RTO. Then the result is documented — what was restored, from which copy, how long
it took, what was checked — so the next audit reads a record instead of a memory.

A full restore recovers everything; a sampled restore recovers a defined subset.
Sampling is legitimate and often the only affordable way to test often, but the
sample has to exercise the real path — the same media, the same decryption, the
same sequence — or it proves only that the easy part works.

| Dimension | Full restore | Sampled restore |
| --- | --- | --- |
| Scope | The whole dataset or system | A defined subset of files or records |
| Proves | The recovery path end to end | The path works for what was sampled |
| Cost | Time, and a full-size clean environment | Cheaper and faster, so run more often |
| The trap | Rare, so the RTO stays untested between runs | A sample that skips the hard parts proves nothing |

## Where restores fail

Every one of these passes the backup dashboard.

**Green for years, then nothing to restore.** The jobs report success for so long
that no one questions them, and the first real restore meets missing media, a
decryption key nobody held or a set that turns out to have never been complete.
The dashboard measured that the job ran, not that its output could be recovered.

**Testing the flag, not the restore.** The "test" checks that the backup job
finished with a success code instead of performing an actual restore. This proves
the software can write a file. It says nothing about whether that file reconstructs
into working data.

**Restoring into the same failure.** The restore is run back into the environment
that failed, reusing its configuration, its keys and its dependencies. It works,
and proves nothing about recovering when that environment is the thing that is
gone — which is the scenario a backup exists for.

**Works in the lab, never timed.** The restore succeeds but was never run against
the clock, so the RTO is a number in a plan that no exercise has ever met. A
recovery time nobody has measured is a guess, and it is usually optimistic.

## Common questions

:::faq
### What is the difference between a backup and a restore test?

A backup is the copy; a restore test is the proof the copy is worth keeping. The
backup is made by a scheduled job and confirmed by that job reporting success —
which only means data was written somewhere. The restore test reads that data back
into a separate environment and confirms it reconstructs into something complete,
usable and recent enough to meet the RPO. One is an activity that runs; the other
is the control that shows the activity was worth running.

### How often should you test restores?

Often enough that the gap between two tests is shorter than the time it would take
a silent failure to matter, and always after a material change to the system, the
backup method or the encryption. A yearly full restore with lighter sampled
restores in between is a common shape, and higher-tier systems are tested more
often — but those figures are examples, not a rule from any standard. The real
cadence follows the criticality set in the BIA and the rate at which the
environment changes; a system that was re-platformed last month should not be
relying on a restore proven against the old one.

### What does a restore test prove?

That a specific backup, restored by a specific path, produced data that was
complete, usable and recent enough to meet the RPO, within the restore time the
RTO budget allows — on the day it was run. Proving the full activity recovery time
still needs an end-to-end exercise; a data restore is one part of it. It does not
prove the next restore will succeed, which is why the test is
repeated and why its result is documented each time. A single successful restore
retires the assumption for one configuration; it does not retire it forever.
:::
